## Key findings (settled)

- **V06 P1 privacy risk (static traced; browser reproduction pending)** - [app-sidebar.tsx:174-180](../../src/components/app-sidebar.tsx) signs out, calls `clearActiveCompany()` (which only clears selection/localStorage), then SPA-navigates to login; [login.tsx:56-75](../../src/routes/login.tsx) signs a new user in and SPA-navigates, reusing the QueryClient created in [src/router.tsx:9-32](../../src/router.tsx). [api-client.ts:78-95](../../src/lib/api-client.ts) uses user-independent query keys (`['companies']`, `['eft','my-requests']`, `['referrals','my']`, `['activity',...]`) and there is no QueryClient clear/cancel at sign-out; [use-active-company.ts:55+](../../src/hooks/use-active-company.ts) falls back to cached `companies[0]`. When user A loads private data, signs out, and user B signs in in the same tab - especially within `staleTime` 30s - components can render A's cached Company/EFT data before any B fetch; API ownership guards do not remove already-cached client data. No observed cross-user leak or unauthorized server access is claimed; the privacy expectation comes from the Company ownership boundary ([lib/ownership.ts](../../src/lib/ownership.ts)) and authenticated routes. Remedy: native QueryClient `clear()`/`cancelQueries` at successful identity transitions (or deliberately a new client per identity), retaining the active-company reset and handling in-flight responses; no new cache abstraction ([official QueryClient API](https://tanstack.com/query/latest/docs/framework/react/reference/classes/QueryClient)). Test: same browser, A -> sign out -> B with a delayed B response never renders A Company/CIPC/EFT data; repeat with an in-flight A request.
- **V01 P1 Wrong (static traced failure, not a claimed production incident)** - ADR0003: "referrer rewarded on first paid subscription confirmation". [confirm.ts:37-87](../../src/routes/api/eft/admin/$paymentId/confirm.ts) commits status/credits, THEN invokes the referral reward at :111-124 and swallows any failure; retry returns early for an already-confirmed payment (:26 or :95) and never retries the missing reward. A transient reward DB failure after payment confirmation has no recovery path. `sendEftDecisionEmail` catches delivery failures internally, so email failure alone does not cause this finding. Preserve prices, reward amounts/caps, and exactly-once credit grant; make reward work durably retryable/atomic with confirmed-payment identity and the first-paid plan preserved; expose a deep public command in existing `lib/eft.ts`/`lib/referral.ts`, not another thin wrapper. Test: failed reward persistence followed by a repeat confirmation produces exactly one original-plan referrer reward, no referee bonus, no double payment credit.
- **V02 P2 security/default gap** - [r2-response.ts:31-55](../../src/lib/r2-response.ts) claims private but emits neither `Cache-Control: private,no-store` nor `X-Content-Type-Options: nosniff`, serving contractor documents/tender files and admin proof through authenticated routes. `Content-Disposition: attachment` on two callers does not make a response non-cacheable, and admin proof requests inline. No demonstrated cross-user exploit is claimed. Default sensitive authenticated files to `private,no-store` and `nosniff` on 200/206/304/412/416, retaining auth ownership and range behavior. The installed Void storage guide recommends nosniff plus attachment for user uploads; the auth guide says keep no-store for data that must not persist after logout. Inline proof needs explicit safe-type handling, not an external preview provider.
- **V03 P2 Partial (test seam)** - most EFT state/credit mutation still lives in confirm/reject/upload routes while `lib/eft.ts` holds only helpers (CODING_STANDARDS Shape requires spend/score/confirm/reward rules in lib). [eft.test.ts:87-114](../../tests/unit/eft.test.ts) implements a local `balanceAfterRenewal` formula and tests that fake, not the production conditional SQL; [reminder-idempotency.test.ts:43-115](../../tests/unit/reminder-idempotency.test.ts) `recordSend` duplicates persistence and tests a UNIQUE/FK constraint, not the public sweep; [sbd.test.ts](../../tests/unit/sbd.test.ts) tests `getSbd4Fields`/`getSbd61Fields` exported only for testing, not the generated PDF; the referrals test reads tables at :102-160 instead of caller-visible balances/stats. Move only the deep rule execution into existing lib modules and drive public commands - no wrapper layer, and keep rules/thresholds unchanged.
- **V04 Partial (credit-refund proof)** - ADR0001 consume-before-store path exists in [analyze.ts:68+](../../src/routes/api/tenders/analyze.ts) with refund catch at :171-191; `credits.test.ts` proves consume/refund primitives. The smoke merely asserts `creditsAfter > creditsBefore` after a purchase (:218-222), so it does not prove exactly one analysis credit consumed or automatic compensation on failure. Add one public-outcome scenario each for failure restoring balance and successful analysis charging exactly once; no AI calls in deterministic domain tests. No claim a normal failure was observed losing a credit.
- **V05 Partial (runtime validation)** - company PATCH and document PATCH parse JSON with casts/manual coercion (company name `null` becomes the literal string "null"; `Boolean("false")` is true) despite installed Zod and the existing `company-validation` module. Prefer shared Zod input schemas for create/PATCH/UI where three consumers exist, preserving legitimate string/number forms and current statutory formats; invalid dates/types should yield actionable 400s. A stack simplification/input-robustness item - not an approved change to money or deadlines.

## 3. Custom vs stack

KEEP: direct Better Auth (Void-managed auth unsupported in Start framework mode - official installed guide); existing Drizzle/native Cloudflare bindings (module scope); Query SSR integration; pdf-lib/unpdf with their maintenance risk and bounding requirements; the migration bridge (proved necessary - Void 1.1.12 refuses existing `d1_migrations` history, see Tests). Candidates: replace the custom SQLite/D1 test facade in `tests/helpers/test-db.ts` with Cloudflare Vitest real D1 for persistence/concurrency semantics (adds a stack test package, removes a handwritten prepare/batch facade; keep pure scoring tests in the lightweight runtime); evaluate replacing the `parseRange` parser with native R2 `range: request.headers` while preserving explicit invalid-range/conditional responses (no untested drop-in claim); manual input coercions -> existing Zod schemas (V05); HTTP JSON client/DTOs -> Start inferred server functions is a potential simplification for JSON reads only - NOT a mandate to rewrite binary/auth/upload endpoints without an originating API spec; Resend fetch/local mailbox could use native Cloudflare/Void email but changing sender resources needs separate human approval (no Resend SDK installed, so no REMOVE verdict).
